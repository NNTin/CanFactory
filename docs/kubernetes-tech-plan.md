# CanFactory Kubernetes tech plan

## Architectural Approach

Status: draft for implementation review, 2026-09-21. Architectural direction was
agreed interactively; the detailed mechanisms below are proposals for that review.
The infrastructure repository's `docs/canfactory/migration-plan.md` holds phases,
ownership, validation, operational procedures, and remaining verification gates.

- Scope is CanFactory and its dependencies on one existing WSL2/NUC host. Shared
  Compose infrastructure and unrelated applications continue operating.
- RKE2 provides Kubernetes; Flux reconciles reviewed Git revisions and immutable
  OCI releases. A reusable application Helm chart packages CanFactory workloads.
- PostgreSQL replaces SQLite for catalogue metadata, jobs, deduplication, leases,
  and heartbeats. No separate broker is introduced.
- Local Garage provides S3-compatible persistent reference and temporary generated
  objects. PostgreSQL and Garage each start as one stateful instance on local PVs.
  Application replication does not provide storage or host high availability.
- Web, API, and workers have independent replica settings. Start at 2/2/1; prove
  operation with at least two API and two worker processes before cutover.
  Each worker executes one OpenSCAD subprocess at a time; autoscaling is deferred.
- A dedicated outbound Cloudflare Tunnel reaches an internal Traefik Service.
  Gateway API routes `/api/*` to API and `/` to static web. Public HTTPS terminates
  at Cloudflare; tunnel transport is encrypted; the in-cluster origin leg is HTTP.
  No public NodePort, LoadBalancer, host-port ingress, or router forwarding is needed.
- Preserve the hostname, public access without Authentik, security headers, model
  customization, browser STL inspection, and downloading the same generated bytes.
- Preserve supplied files, CC BY-SA attribution, source availability, model
  extensibility, validation, fingerprints, deduplication, leases, fencing, and recovery.
- Temporary jobs, settings, and generated files expire one hour from submission.
  References persist. Initial migration and host-loss recovery start with an empty
  temporary queue/cache; short interruptions are accepted.
- API/queue/artifact operations become asynchronous. Use bounded database pools,
  request timeouts, streaming downloads, and cancellable object operations.
- Database migrations and seeding move out of API startup into a serialized release
  Job. A separate scheduled maintenance command handles expiry and object cleanup.
  Worker lease recovery remains safe for concurrent callers.
- Normal rolling updates require compatible schema and unchanged model/renderer
  fingerprints. Fingerprint-changing releases use a submission pause and queue drain.
- No credentials are stored in Git or chart values. Bootstrap provisions named
  Kubernetes Secrets through protected local inputs. Kubernetes secret encryption
  at rest is enabled; credentials are scoped by component and purpose.
- Local rollback copies and a tested rebuild are the recovery strategy. There is
  no off-machine backup or promise of survival of a complete host/disk failure.

## Data Model

Use versioned PostgreSQL SQL migrations with an advisory lock. Preserve public
millisecond timestamps and API contracts; use database time for lease/expiry
decisions to avoid disagreement between replicas.

| Entity | Purpose and constraints |
| --- | --- |
| Model revisions | Immutable model ID/version/source hash, schema, controls, defaults, attribution, reference-object key and SHA-256; retain revisions required by active jobs |
| Catalogue activation | Transactionally select a release's available revisions; repeated seeding is idempotent and never rewrites supplied bytes |
| Render jobs | UUID, unique cache identity, normalized parameters, source and renderer fingerprints, status, created/expiry times, attempts, fencing token, lease deadline, result metadata or sanitized error |
| Workers | Process UUID, supported release/fingerprints, heartbeat; stale rows expire |
| Object deletion tasks | Object key and retry metadata only; no settings or STL payloads; survive failed deletion after job removal |
| Schema migrations | Applied migration IDs; release startup checks the supported schema range |

Catalogue objects use immutable content-addressed keys. Generated objects use an
immutable key per job attempt, not an overwriteable job-only key. Keep catalogue
and generated data in separate buckets with separately scoped credentials.

Submission is a transaction: normalize and validate settings, derive the full
fingerprint, reuse an unexpired queued/running/succeeded job, or replace an
expired/failed entry. Serialize queue admission using a database advisory lock;
the unique cache constraint is a second defense. Queue capacity remains 16 queued
jobs across all APIs, not 16 per replica. Object deletion is scheduled durably.

Claim the oldest eligible unexpired job with `FOR UPDATE SKIP LOCKED`, then assign
a fresh token, increment attempts, and commit. Claims filter on worker-supported
model/source/renderer fingerprints. Renew every five seconds for a 30-second lease.
Renewal, success, and failure updates check token, running status, live lease, and
job expiry. Recovery atomically requeues the first abandoned attempt and marks a
second interruption failed; concurrent recoverers cannot increment retries twice.

Successful publication is deliberately split:

1. Render in pod-local scratch, validate the STL and attribution, compute metadata.
2. Upload under an immutable attempt key; keep renewing the lease during upload.
3. Conditionally record success and object metadata inside a transaction while
   checking the live fencing token and deadline. Only the winning row is visible.
4. If publication loses its lease or fails, enqueue object deletion; a periodic
   orphan scan also collects uploads left by crashes before deletion was recorded.

The object store and PostgreSQL cannot commit atomically. Cleanup must not delete
an in-flight upload or a published object: recheck database references/active
attempts and use a grace period longer than the bounded render/upload attempt.
No claim may publish after expiry. Establish a bounded upload timeout in tests.

API reads reject expired/missing jobs immediately with the existing 410 behavior.
Maintenance runs every minute under a PostgreSQL advisory lock, deletes expired
settings/records, retries deletion tasks, and sweeps abandoned objects. Physical
cleanup can lag logical expiry; failed cleanup is observable and retried.
No long-lived backup includes temporary job settings or generated objects.

## Component Architecture

| Component | Responsibilities and interfaces |
| --- | --- |
| Web Deployment + Service | Static React/Three.js build; no Docker DNS or API proxy in the Kubernetes configuration; preserve SPA routing and asset caching |
| API Deployment + Service | Validation, catalogue/status, enqueue, same-origin reference/generated STL streaming; async store and object interfaces |
| Worker Deployment | Poll/claim, recover leases, heartbeat, render, upload and fenced completion; no inbound application Service |
| Release Job | `migrate` and `seed` commands under a database lock; verify reference hashes and upload before catalogue activation |
| Maintenance CronJob | `cleanup` command; non-overlapping schedule plus DB lock; durable retry of object deletion and orphan collection |
| PostgreSQL StatefulSet + Service | Single queue/metadata authority; bounded connections and persistent local volume |
| Garage StatefulSet + Service | Single-node S3 API and persistent local data/metadata; administrative bootstrap stays private |
| Traefik + Gateway/HTTPRoute | Internal ingress, path routing and response security headers; no authentication middleware |
| cloudflared Deployment | Dedicated tunnel connector; outbound access to Cloudflare, internal access to Traefik |

`RenderQueue` becomes a Promise-based contract for enqueue, claim, renew, complete,
fail, and recover. `ArtifactStore` exposes upload, head, streaming read, delete,
and paginated listing; it never exposes a shared local artifact path to API code.
The renderer continues accepting trusted model definitions and allowlisted
argument arrays; only its scratch path and publication interface change.

API liveness checks process health without depending on workers. Readiness checks
schema compatibility and required data services. Keep `/api/health` compatible and
add explicit probe endpoints as needed. A stopped worker must not make catalogue
and existing downloads disappear. Worker probes inspect local heartbeat progress;
transient storage failures cause retries/backoff rather than probe restart storms.

On SIGTERM, API stops accepting requests and closes connections after in-flight
responses; workers stop claiming, abort the subprocess/upload, and leave the claim
for lease recovery. Preserve a finite termination grace period and test SIGKILL.
Worker rolling updates use zero surge to respect the render-concurrency limit.

The chart owns a pre-install/pre-upgrade migration/seeding hook Job. Its required
Secrets and backing services exist before Helm runs; any hook-only ServiceAccount
or configuration is also hook-managed with explicit ordering and deletion policy.
API startup never migrates/seeds. A failed hook prevents rollout. Hooks and Helm
rollback do not undo SQL migrations; only backward-compatible migrations roll back
automatically. Incompatible changes require a separately reviewed maintenance step.

Expose private queue depth, oldest queued age, running jobs, healthy workers,
render duration/failures, lease recoveries, and cleanup backlog metrics. Queue
gauges describe shared state and must not be summed across API replicas. Keep
metrics off the public HTTPRoute and avoid a new monitoring stack in this phase.

Validation includes real PostgreSQL/Garage concurrency tests, real pinned OpenSCAD,
cross-replica preview/download hash equality, deletion retry, interruption/fencing,
one-hour expiry, reference integrity, and compatible/incompatible release upgrades.
